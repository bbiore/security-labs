# Milestone 2: Network Traffic Capture and Protocol Identification

## Purpose

Milestone 2 focused on capturing and analyzing traffic generated by the Govee H6008 smart bulb and the Govee Home app during normal use.

## Capture Methods

Tools and techniques used included:

- Wireshark
- tcpdump
- TLS handshake inspection
- DNS and SNI analysis
- Wireshark display filters
- Traffic timing correlation
- BLE scanning with Linux tools

## Observed Communication Pattern

The key traffic pattern was:

```text
Govee Home App -> Govee Cloud over HTTPS 443
Govee Cloud / AWS IoT -> Bulb over MQTT/TLS 8883
```

No direct LAN command path was observed between the phone app and the bulb.

## Important Findings

### Encrypted traffic still exposes metadata

TLS protected the command payloads, but useful metadata remained visible, including:

- Destination IP addresses
- Destination ports
- Packet timing
- Packet size
- TLS SNI fields where available
- Traffic bursts tied to app actions

### Cloud-mediated control was confirmed

Each user action produced app-to-cloud HTTPS traffic followed by cloud-to-bulb MQTT/TLS traffic.

### BLE advertisements persisted

The bulb continued broadcasting BLE advertisements after Wi-Fi pairing, exposing a secondary discovery surface.

## Representative Protocols

| Protocol | Port | Observed Purpose |
| --- | --- | --- |
| HTTPS | TCP 443 | App-to-cloud communication |
| MQTT over TLS | TCP 8883 | Cloud-to-device messaging |
| DNS | UDP 53 | Hostname resolution where visible |
| BLE | N/A | Device discovery and pairing |

## Skills Practiced

- Packet capture collection
- Protocol identification
- Encrypted traffic analysis
- Timing-based traffic correlation
- IoT metadata analysis
- BLE advertisement observation

## Main Takeaway

Even when IoT traffic is encrypted, network metadata can still reveal how a device communicates and when user actions occur.
